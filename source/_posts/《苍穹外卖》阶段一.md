## 答案批改

### 问题一：✅ 方向正确，但核心原因没说到点子上

你说的"产生冲突"是对的，但原因描述得不够精准，我帮你补全：

`JwtTokenAdminInterceptor` 是一个 **Spring 单例 Bean**（`@Component` 默认单例）。  
单例意味着：**整个应用只有一个拦截器对象**。

想象一下：

```
用户A的请求 → 同一个拦截器对象 → 成员变量 empId = 1001
用户B的请求 → 同一个拦截器对象 → 成员变量 empId = 1002  ← 把A的值覆盖了！
```

两个请求并发执行，共享同一个对象的成员变量，就会**互相覆盖**，这就是**线程安全问题**。

而 `ThreadLocal` 的核心价值是：**每个线程拥有自己独立的一份数据，互不干扰**。用户A的线程存的 `empId=1001`，用户B的线程绝对取不到。

## 答案批改

### 问题二：✅ 结论正确，对底层原理的困惑很正常，我现在解释

你说"只有调用 remove 才能清除"，完全正确。  
现在我用最简单的比喻解释你不懂的三个概念：

**① 什么是线程池？（理解"线程复用"）**

不用线程池：每来一个请求就新建一个线程，用完就销毁。  
用线程池：提前准备好 20 个线程，请求来了从池里取一个用，**用完放回去**，下一个请求继续用这个线程。

所以：**线程不会销毁，它会一直活着**。

```
第1次请求（线程A处理）→ ThreadLocal 存入 empId=1001 → 请求结束，但线程A没死
第2次请求（线程A被复用）→ ThreadLocal 里还有上次的 empId=1001！← 数据污染
```

这就是为什么必须在请求结束时调用 `remove()`。

---

**② 什么是强引用 vs 弱引用？（理解内存泄漏）**

```java
// 强引用：只要变量存在，对象就不会被GC回收
Employee e = new Employee(); // e 是强引用，GC 不敢动这个对象

// 弱引用：GC 只要发现它，不管内存够不够，都会回收
WeakReference<Employee> weakE = new WeakReference<>(new Employee());
```

**ThreadLocalMap 的结构（你笔记里的那段）：**

```
Thread
  └── ThreadLocalMap
        └── Entry: key=ThreadLocal对象(弱引用), value=empId(强引用)
```

`key`（ThreadLocal 对象）是弱引用 → GC 会把它回收 → `key = null`  
`value`（empId 的值）是强引用 → GC **不敢**回收 → 内存泄漏

这就是你笔记里那段的意思。

---

**③ 什么是内存泄漏？**

程序不再需要某块内存，但它无法被 GC 回收，这块内存就被"占着茅坑不拉屎"了。  
线程池线程永远不死 + value 强引用 = **这块内存永远不会被释放** = 内存泄漏。

```java
Map<String, Object> claims = new HashMap<>();
claims.put(JwtClaimsConstant.EMP_ID, employee.getId());
String token = JwtUtil.createJWT(
        jwtProperties.getAdminSecretKey(),
```

## 我的回答

1. claims中存放了empId员工ID，这和AdminSecretKey,AdminTtl都是JWT的token的组成部分，jwt拦截器需要调用JwtUtil.parseJWT方法校验token中的验证签名，过期时间，员工or用户id，所以需要把empId放进去。
2. jwtProperties类是一个配置类，通过读取application.yml中的sky.jwt信息获得jwt相关参数，用于生成和校验JWT令牌jwtProperties.getAdminSecretKey()和 jwtProperties.getAdminTtl()分别用于获取配置文件中的jwt签名密钥和jwt过期时间。

## 答案批改

### 问题一：⚠️ 方向对，但有一个概念性错误

你说"claims、SecretKey、TTL 都是 JWT token 的组成部分"——**不准确**。

JWT 由三部分组成：`Header.Payload.Signature`

- [claims](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html)（载荷/Payload）→ ✅ 是 token 的一部分，存在 token **里面**
- `SecretKey`（密钥）→ ❌ **不是** token 的组成部分！密钥只存在**服务端**，用来**签名和验签**，永远不会出现在 token 中
- `TTL`（过期时间）→ 它会被转化为 `exp` 字段写入 Payload 中

简单说：

```
生成 token 时：
  SecretKey + claims + TTL  →  JwtUtil.createJWT()  →  输出一个 token 字符串

校验 token 时：
  SecretKey + token字符串   →  JwtUtil.parseJWT()   →  解析出 claims
                                                       → 同时校验签名和过期
```

至于为什么要把 [empId](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 放进去，你说的对——拦截器后续要从 token 中取出 [empId](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 存入 ThreadLocal，所以生成时必须放进去。


---

### 问题二：✅ 完全正确

[JwtProperties](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 通过 `@ConfigurationProperties` 读取 `application.yml` 中的配置，[getAdminSecretKey()](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 获取签名密钥，[getAdminTtl()](vscode-file://vscode-app/c:/Lin%20de%20study/Microsoft%20VS%20Code/072586267e/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 获取过期时间。理解到位。

# 破坏性测试

非常好的想法！**破坏性测试是最高效的学习方式之一。** 面试官问的很多"如果不这样做会怎样"的问题，就是你通过这些实验能直接回答的。

## 实验一：注释掉 `excludePathPatterns`

**改动位置：** WebMvcConfiguration.java

```java

        .addPathPatterns("/admin/**");
        // .excludePathPatterns("/admin/employee/login");  ← 注释掉
```
