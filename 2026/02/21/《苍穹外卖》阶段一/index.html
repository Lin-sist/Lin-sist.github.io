问题一（理解 ThreadLocal 的作用）

拦截器解析 JWT 成功后，从 token 里拿到了 empId。
请问：这个 empId 应该存在哪里？为什么不能存在拦截器的成员变量里？
（提示：同一时刻，服务器在处理多少个请求？）

我的回答

问题一：
看代码前我完全说不出任何东西，但是我初略看了一下代码，我认为拿到empid后，empid会存放在ThreadLocal里面；
翻看笔记复习一下什么是ThreadLocal:
threadlocal是Java提供的线程局部变量，它为每个线程提供独立的变量副本，不用threadlocal时，想得到某个变量就得显式声明，用threadlocal就可以直接调用get方法直接获取，让代码更加简洁高效。
为什么步放在拦截器成员变量中？

  1. 代码臃肿，不利于优化，容易漏写。
  2. 如果放在拦截器成员变量中，在同一时刻，用户请求其他服务时，会产生冲突无法获得用户id(我对jwt登录流程不熟悉，请指正)

答案批改

问题一：✅ 方向正确，但核心原因没说到点子上

你说的”产生冲突”是对的，但原因描述得不够精准，我帮你补全：

JwtTokenAdminInterceptor 是一个 Spring 单例 Bean（@Component 默认单例）。
单例意味着：整个应用只有一个拦截器对象。

想象一下：

两个请求并发执行，共享同一个对象的成员变量，就会互相覆盖，这就是线程安全问题。

而 ThreadLocal 的核心价值是：每个线程拥有自己独立的一份数据，互不干扰。用户A的线程存的 empId=1001，用户B的线程绝对取不到。

问题二（理解资源清理的必要性）

假设我在拦截器的 preHandle 里调用了 BaseContext.setCurrentId(empId)，把用户ID存进去了。
那么当这个HTTP 请求处理完毕之后，这条数据会自动消失吗？
如果不清理，会发生什么？
（提示：Spring Web 默认使用线程池，线程是复用的）

我的回答

问题二：
不会消失，如果不清理，这个线程会一直存在，这条数据存在这个线程中故也会一直存在，只有使用remove方法才可以清除这个线程及其数据。
翻看笔记知道：
threadlocal的底层原理是“thread对象包含threadlocalmap这个数据结构，key为threadlocal对象，value为该对象存储的值”。ThreadLocal对象会被GC回收（因为key是弱引用），回收后key为空，但是value还是强引用，无法被GC，线程池场景下，线程不销毁，value永远不会被回收 这回导致内存泄漏（这段是摘抄笔记的，但是我不理解什么是强引用，弱引用，什么是线程池和内存泄漏）
以上就是我的回答，帮我纠正并解答我的问题。

答案批改

问题二：✅ 结论正确，对底层原理的困惑很正常，我现在解释

你说”只有调用 remove 才能清除”，完全正确。
现在我用最简单的比喻解释你不懂的三个概念：

① 什么是线程池？（理解”线程复用”）

不用线程池：每来一个请求就新建一个线程，用完就销毁。
用线程池：提前准备好 20 个线程，请求来了从池里取一个用，用完放回去，下一个请求继续用这个线程。

所以：线程不会销毁，它会一直活着。

这就是为什么必须在请求结束时调用 remove()。

② 什么是强引用 vs 弱引用？（理解内存泄漏）

ThreadLocalMap 的结构（你笔记里的那段）：

key（ThreadLocal 对象）是弱引用 → GC 会把它回收 → key = null
value（empId 的值）是强引用 → GC 不敢回收 → 内存泄漏

这就是你笔记里那段的意思。

③ 什么是内存泄漏？

程序不再需要某块内存，但它无法被 GC 回收，这块内存就被”占着茅坑不拉屎”了。
线程池线程永远不死 + value 强引用 = 这块内存永远不会被释放 = 内存泄漏。

现在，请你自己找 Bug

你现在已经理解了 ThreadLocal 的完整理论。
回头打开这个文件：JwtTokenAdminInterceptor.java

对照你刚学的知识，仔细读 preHandle 方法，回答我：

1. empId 被解析出来了，但下一步发生了什么？代码里缺少了哪一行？

2. 整个拦截器里，防止内存泄漏的那个 remove() 调用，应该写在哪个方法里？（提示：HandlerInterceptor 接口除了 preHandle，还有哪些方法？）

自己先找，找到之后告诉我，我们再一起修。

🔑 关键词备忘（加入 Obsidian）

  • ThreadLocal — 线程局部变量
  • ThreadLocalMap — Thread 对象内部持有的 Map 结构
  • WeakReference — 弱引用，Java 四种引用类型之一（强/软/弱/虚）
  • 内存泄漏 (Memory Leak) — 无用内存无法被 GC 回收

问题三（登录流程）

当一个 POST 请求发到 /admin/employee/login 时，它依次经过了哪些组件？请按顺序列出来。

（提示：从请求进入 Tomcat 开始，到 Controller 方法返回 JSON 结束，中间有哪些”关卡”？拦截器会不会拦截登录接口？）

我的回答

翻看我的笔记我看到，当前端传来登录请求时，登录接口被WebMvcConfiguration类的excludePathPatterns排除了，所以不会被拦截器拦截（但是我没有在WebMvcConfiguration类中看到excludePathPatterns）。
前端请求来到EmployeeController由注解@PostMapping(“/login”)得知让login方法来处理这个请求，然后生成JWT令牌（具体的流程我不太懂，包括什么DTO,VO生成JWT具体调用的类和方法等）我说个大概：login用employeeLoginDTO将请求传递到service层调用EmployeeServiceImpl的方法，在通过mapper层比对数据库数据以employee对象的形式从数据库返回到mapper层在返回到service层进行校验，校验成功返回到controller层将对象封装为employeeLoginVO只显示需要的数据，最后返回前端。以后前端需要做其他操作时会自动携带jwt令牌token，拦截器就在做操作前进行令牌校验决定通行or放行。我翻看笔记后的理解如下，帮我检查并纠正。

答案批改

① “login 用 employeeLoginDTO 将请求传递到 service 层”
✅ 正确。但要补充：EmployeeLoginDTO 不是 Controller 自己创建的，是 Spring MVC 通过 @RequestBody 注解，把前端发来的 JSON 自动反序列化成 Java 对象的。

② “通过 mapper 层比对数据库数据”
❌ 不准确。Mapper 层只负责查询，不负责”比对”。来看真实流程：

核心区别：Mapper = 数据搬运工，Service = 业务逻辑判断者。 这是分层架构的核心思想。

③ “校验成功返回到 controller 层将对象封装为 employeeLoginVO 只显示需要的数据”
✅ 正确！Employee 是数据库实体（包含密码等敏感字段），EmployeeLoginVO 只暴露 id、userName、name、token，这就是 VO 的意义——控制返回给前端的数据范围。

④ “以后前端会自动携带 jwt 令牌 token，拦截器进行令牌校验决定通行 or 放行”
✅ 方向对，但措辞要精确：不是”自动携带”，是前端代码把 token 存在本地（如 localStorage），之后每次请求主动放到请求头（Header）里带过来。拦截器从 Header 中取出 token 进行校验。

问题四（生成 JWT流程）

  1. claims 这个 Map 里放了什么？为什么要把 empId 放进去？（提示：以后拦截器要从 token 里取什么？）
  2. jwtProperties.getAdminSecretKey() 和 jwtProperties.getAdminTtl() 分别是什么含义？（提示：TTL 是 Time To Live）

我的回答

  1. claims中存放了empId员工ID，这和AdminSecretKey,AdminTtl都是JWT的token的组成部分，jwt拦截器需要调用JwtUtil.parseJWT方法校验token中的验证签名，过期时间，员工or用户id，所以需要把empId放进去。
  2. jwtProperties类是一个配置类，通过读取application.yml中的sky.jwt信息获得jwt相关参数，用于生成和校验JWT令牌jwtProperties.getAdminSecretKey()和 jwtProperties.getAdminTtl()分别用于获取配置文件中的jwt签名密钥和jwt过期时间。

答案批改

问题一：⚠️ 方向对，但有一个概念性错误

你说”claims、SecretKey、TTL 都是 JWT token 的组成部分”——不准确。

JWT 由三部分组成：Header.Payload.Signature

  • claims（载荷/Payload）→ ✅ 是 token 的一部分，存在 token 里面
  • SecretKey（密钥）→ ❌ 不是 token 的组成部分！密钥只存在服务端，用来签名和验签，永远不会出现在 token 中
  • TTL（过期时间）→ 它会被转化为 exp 字段写入 Payload 中

简单说：

至于为什么要把 empId 放进去，你说的对——拦截器后续要从 token 中取出 empId 存入 ThreadLocal，所以生成时必须放进去。

问题二：✅ 完全正确

JwtProperties 通过 @ConfigurationProperties 读取 application.yml 中的配置，getAdminSecretKey() 获取签名密钥，getAdminTtl() 获取过期时间。理解到位。

破坏性测试

非常好的想法！破坏性测试是最高效的学习方式之一。 面试官问的很多”如果不这样做会怎样”的问题，就是你通过这些实验能直接回答的。

我给你设计一套 **”搞破坏实验清单”**，每个实验都对应一个核心知识点：

实验一：注释掉 excludePathPatterns

改动位置： WebMvcConfiguration.java

预测一下： 你尝试调用登录接口会发生什么？HTTP 状态码是多少？

你会学到： 登录接口自己也在 /admin/** 路径下，如果不排除，请求在到达 Controller 之前就被拦截器挡住了，而此时用户还没有 token。这是一个”鸡生蛋蛋生鸡”的问题。

实验二：注释掉 BaseContext.setCurrentId(empId)

改动位置： JwtTokenAdminInterceptor.java

现在还测不出明显效果（因为登录接口没用到 BaseContext），但等你敲到”新增员工”时，Service 里会调用 BaseContext.getCurrentId() 来获取”谁创建了这条记录”。到那时再回来做这个实验，你会看到 createUser 字段为 null 或者报 NPE。

你会学到： 拦截器和 Service 之间通过 ThreadLocal 隐式传递数据，断开任何一环都会出问题。

实验三：注释掉 GlobalExceptionHandler

改动位置： GlobalExceptionHandler.java

把类上的 @RestControllerAdvice 注释掉：

然后用一个错误的用户名去登录，预测：

  • 有全局异常处理器时，前端收到什么？
  • 没有时，前端收到什么？

你会学到： 没有全局异常处理器时，Spring 会返回一坨原始的错误页面（Whitelabel Error Page）或 500 错误 JSON，对前端极不友好。全局异常处理器的作用就是把异常统一包装成前端能识别的 Result 格式。

实验四：去掉密码的 MD5 加密

改动位置： EmployeeServiceImpl.java

用正确的账号密码登录，预测： 能登录成功吗？

你会学到： 数据库里存的是 MD5 密文（如 e10adc3949ba59abbe56e057f20f883e），你传入的是明文 123456，明文 ≠ 密文，所以密码校验一定失败。这让你直观感受到：加密必须在比对之前做，而且加密方式必须和入库时一致。

实验五：去掉 @RequestBody

改动位置： EmployeeController.java

用 Postman 发送 JSON 请求体登录，预测： employeeLoginDTO 里的 username 和 password 是什么？

你会学到： 没有 @RequestBody，Spring 不会从请求体解析 JSON，而是尝试从 URL 参数绑定。结果 username=null, password=null，直接报”账号不存在”。这就是 @RequestBody 的核心作用。

实验六：把 JWT 密钥改错

改动位置： application-dev.yml 中的 sky.jwt.admin-secret-key

随便改成别的字符串。

先正常登录拿到 token，然后用这个 token 去请求其他接口，预测： 会发生什么？

你会学到： 生成 token 用的是旧密钥，验证时用新密钥，签名校验失败，拦截器抛异常返回 401。这就是为什么密钥不能随便改、不能泄露。

实验操作建议

顺序 实验 难度 预计耗时
1 实验四（去掉MD5） ⭐ 2分钟
2 实验五（去掉@RequestBody） ⭐ 3分钟
3 实验三（去掉异常处理器） ⭐⭐ 5分钟
4 实验一（去掉排除路径） ⭐⭐ 3分钟
5 实验六（改JWT密钥） ⭐⭐ 5分钟
6 实验二（去掉setCurrentId） ⭐⭐⭐ 新增员工后再做

每个实验的流程：

  1. 先预测结果（写下来）
  2. 注释代码，重启项目
  3. 用 Knife4j（localhost:8080/doc.html）或 Postman 测试
  4. 对比预测和实际结果，不一致的地方就是你的知识盲区
  5. 恢复代码，进入下一个实验

做完这些实验后告诉我你的发现，特别是预测错误的那些——那才是最有价值的学习点。然后我们正式进入第二阶段”新增员工”。
