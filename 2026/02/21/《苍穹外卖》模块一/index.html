问题一（理解 ThreadLocal 的作用）

拦截器解析 JWT 成功后，从 token 里拿到了 empId。
请问：这个 empId 应该存在哪里？为什么不能存在拦截器的成员变量里？
（提示：同一时刻，服务器在处理多少个请求？）

我的回答

问题一：
看代码前我完全说不出任何东西，但是我初略看了一下代码，我认为拿到empid后，empid会存放在ThreadLocal里面；
翻看笔记复习一下什么是ThreadLocal:
threadlocal是Java提供的线程局部变量，它为每个线程提供独立的变量副本，不用threadlocal时，想得到某个变量就得显式声明，用threadlocal就可以直接调用get方法直接获取，让代码更加简洁高效。
为什么步放在拦截器成员变量中？

  1. 代码臃肿，不利于优化，容易漏写。
  2. 如果放在拦截器成员变量中，在同一时刻，用户请求其他服务时，会产生冲突无法获得用户id(我对jwt登录流程不熟悉，请指正)

答案批改

问题一：✅ 方向正确，但核心原因没说到点子上

你说的”产生冲突”是对的，但原因描述得不够精准，我帮你补全：

JwtTokenAdminInterceptor 是一个 Spring 单例 Bean（@Component 默认单例）。
单例意味着：整个应用只有一个拦截器对象。

想象一下：

两个请求并发执行，共享同一个对象的成员变量，就会互相覆盖，这就是线程安全问题。

而 ThreadLocal 的核心价值是：每个线程拥有自己独立的一份数据，互不干扰。用户A的线程存的 empId=1001，用户B的线程绝对取不到。

问题二（理解资源清理的必要性）

假设我在拦截器的 preHandle 里调用了 BaseContext.setCurrentId(empId)，把用户ID存进去了。
那么当这个HTTP 请求处理完毕之后，这条数据会自动消失吗？
如果不清理，会发生什么？
（提示：Spring Web 默认使用线程池，线程是复用的）

我的回答

问题二：
不会消失，如果不清理，这个线程会一直存在，这条数据存在这个线程中故也会一直存在，只有使用remove方法才可以清除这个线程及其数据。
翻看笔记知道：
threadlocal的底层原理是“thread对象包含threadlocalmap这个数据结构，key为threadlocal对象，value为该对象存储的值”。ThreadLocal对象会被GC回收（因为key是弱引用），回收后key为空，但是value还是强引用，无法被GC，线程池场景下，线程不销毁，value永远不会被回收 这回导致内存泄漏（这段是摘抄笔记的，但是我不理解什么是强引用，弱引用，什么是线程池和内存泄漏）
以上就是我的回答，帮我纠正并解答我的问题。

答案批改

问题二：✅ 结论正确，对底层原理的困惑很正常，我现在解释

你说”只有调用 remove 才能清除”，完全正确。
现在我用最简单的比喻解释你不懂的三个概念：

① 什么是线程池？（理解”线程复用”）

不用线程池：每来一个请求就新建一个线程，用完就销毁。
用线程池：提前准备好 20 个线程，请求来了从池里取一个用，用完放回去，下一个请求继续用这个线程。

所以：线程不会销毁，它会一直活着。

这就是为什么必须在请求结束时调用 remove()。

② 什么是强引用 vs 弱引用？（理解内存泄漏）

ThreadLocalMap 的结构（你笔记里的那段）：

key（ThreadLocal 对象）是弱引用 → GC 会把它回收 → key = null
value（empId 的值）是强引用 → GC 不敢回收 → 内存泄漏

这就是你笔记里那段的意思。

③ 什么是内存泄漏？

程序不再需要某块内存，但它无法被 GC 回收，这块内存就被”占着茅坑不拉屎”了。
线程池线程永远不死 + value 强引用 = 这块内存永远不会被释放 = 内存泄漏。

现在，请你自己找 Bug

你现在已经理解了 ThreadLocal 的完整理论。
回头打开这个文件：JwtTokenAdminInterceptor.java

对照你刚学的知识，仔细读 preHandle 方法，回答我：

1. empId 被解析出来了，但下一步发生了什么？代码里缺少了哪一行？

2. 整个拦截器里，防止内存泄漏的那个 remove() 调用，应该写在哪个方法里？（提示：HandlerInterceptor 接口除了 preHandle，还有哪些方法？）

自己先找，找到之后告诉我，我们再一起修。

🔑 关键词备忘（加入 Obsidian）

  • ThreadLocal — 线程局部变量
  • ThreadLocalMap — Thread 对象内部持有的 Map 结构
  • WeakReference — 弱引用，Java 四种引用类型之一（强/软/弱/虚）
  • 内存泄漏 (Memory Leak) — 无用内存无法被 GC 回收
